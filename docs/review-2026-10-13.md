## 修复前的结论（汇总者）

结论：整体视觉 7.0、交互 6.0、链路 5.5。接入、接待、工单、开票这几条主流程都能走通，主要问题在两处。一是钱：发票合计不含运费；会话里开票能把别的买家的订单发进当前聊天；Shopee 退货退款在货还没寄回时就能一键退款，而且这个选项默认选中。二是权限：员工能读到已改派给同事的会话，还能作废对方的 AI 草稿；员工抢认领失败时看到的是 404，没有说明是谁认领了。工作台是客服停留最久的页面，还会丢内容：与分页边界同一秒的消息被静默漏掉；轮询失败一次，对话栏和输入框整块被换成错误态，没发出的回复就没了。

打分依据：11 个区域直接平均是视觉 7.4、交互 6.5、链路 6.3。我没有用平均分，而是按真实使用影响加权：
- 权重最高：工作台两个区域和 e2e-service 链路。客服大部分时间在这里，P1 也集中在这里（长链接撑破气泡、轮询失败丢输入、同秒消息丢失、越权读取与作废草稿、认领冲突 404）。
- 其次：订单与开票，因为错误直接落到金额和买家隐私上。
- 最低：管理页与认证页，使用频次低。

三项下调的具体原因：
- 视觉 7.4 降到 7.0：三处版式问题都在高频页面上，分别是长链接撑破气泡、1280 宽侧栏展开时对话栏只剩 346px、矮屏下侧栏把当前导航项裁掉。
- 交互 6.5 降到 6.0：所有用 URL 打开的弹层关闭后焦点都丢回 body，这是系统性问题；工作台还会在轮询失败、改派、认领冲突时静默丢掉输入。
- 链路 6.3 降到 5.5：金额错误、跨买家发票、货未寄回先退款都不可逆，比文案类问题严重得多。

去重与分组：约 240 条发现去重后，放进修复组 70 条：server 17、workbench 16、orders-tickets 11、admin-pages 8、shell-shared 18；另有设计提案 26 条、暂缓 25 条。去重量最大的几类：对话框关闭按钮读作英文 Close（8 个区域重复报）、URL 弹层焦点不回触发按钮（5 个区域）、历史会话消息数恒为 0（3 个区域）、表格在 1024/1280 宽溢出（4 个区域）。

跨组依赖：
- S-01 与 S-02 必须同批上线：先收紧员工可见性再改 409，否则认领冲突会全部变成 404。
- W-08 依赖 S-01。
- O-01 与 W-09 按 O-01 里约定的 InvoiceSheet 新属性对接，S-04 是服务端兜底校验。
- S-06 与 W-07 一起修列表重复行。

有三个 P1 只能走设计提案：发票合计含运费（DP-01）、Shopee 售后各状态可用动作（DP-07，修复组 O-04 先去掉默认选中做止血）、会话晚于工单建立时回填 conversation_id（DP-08）。

不属于任何组、要主会话处理的文件：
- src/app/not-found.tsx（404 页）。
- package.json（二维码依赖）。
- src/worker 与 scripts：S-12 已改为只动 src/server/jobs/boss.ts 来绕开。
- docs：H-02 要补 DESIGN API-AUTH-008 与 TEST TC-AUTH-015；S-12 要补 TEST §3 复位后如何确认定时任务在跑。

派发前端组时，任务里要写明加载 ui-constraints；server 组不能改 src/contracts。

测试环境有遗留，下一轮评审前要重新授权或执行 db:reset：模拟应用 2001001 的推送回调现在指向 e2e-onboard 自建商户，E2E 商户 Wizard 店的 token 已作废。

## 需要拍板的设计提案（26 条，未实施）

这些问题按现行设计修不了，要改需求、接口或数据模型，按项目纪律先由用户确认再改设计文档与代码。每条的「默认方案」是评审者给的推荐。

### DP-01 发票与收据的合计要包含运费与优惠（P1）

来源：orders-01、e2e-ops-02。现在合计只算商品行：订单 MYR 43.40（含运费 4.90）开出的发票是 MYR 38.50，Receipt 上印的「Total paid」与买家实付对不上，侧栏的商品行也不能编辑。要在 DESIGN API-INV-002 与 invoice.fields 加运费和优惠字段，这会改 contracts。默认方案：从订单镜像预填 shippingFee、discount 两行，PDF 与聊天图片在 Subtotal 下列出这两行；服务端校验 Receipt 合计等于 order.total_amount，不等时拒绝并说明原因。可以参考 Obsbot v2 InvoiceDialog 的独立「实付金额」字段。

### DP-02 Invoice 上要印开票方的法定名称、地址与税号

来源：orders-25。现在 PDF 卖家侧只有商户名和店铺名，买家拿去报销或抵税用不了。默认方案：在商户设置的商户资料里增加法定名称、地址、税号，允许按店铺覆盖；没填时开票侧栏给出提示。需要修改 REQ-ORD-006 和数据模型。

### DP-03 同一个平台应用或店铺被第二个商户接走时的规则

来源：shops-reception-01（P2，评审中已对共享环境造成实际干扰）。第二个商户填入同一组凭证，会静默改写推送回调，原商户的 token 作废，买家消息进了别的商户，两个商户还会来回抢回调。默认方案：isOurs 收紧为「等于本商户这个 platform_app 的回调地址」；回调指向其他商户时，按 callback-occupied 走确认流程并写明对方商户名；授权回调遇到已在其他商户 connected 的 (platform, external_shop_id) 时，返回 302 reason=owned_elsewhere。需要在 REQ-SHOP-002、REQ-SHOP-004 补上跨商户占用的规则。

### DP-04 员工的工单、会话可见范围要与界面上的入口一致

来源：tickets-01、tickets-02、e2e-ops-04、orders-13。员工在会话右栏、409 去重弹层、发票记录、工单关联卡里都能看到可点的链接，点进去是 404，因为对方对象他没有权限看。默认方案：对「关联会话由本人处理的工单」和「本人负责的工单所关联的会话」开放只读详情。不扩权时的备选：所有不可见的对象只渲染纯文本，如「T-1022 · Arif Rahman 跟进」，同时 API-INV-003 的 ticket 字段按可见范围裁剪。需要修改 DESIGN §10 行级可见性与 §13 PAGE-WB-TICKET；定下方案后再分给 workbench、orders-tickets、server 三组。

### DP-05 先手动建的退货退款工单，要与之后的平台退货事件合并

来源：tickets-03（P2）。先手动建「退货退款」，平台再推退货时会生成第二张工单，同一订单同时有两张未结工单。原因：手动单的去重键是 return_refund:<order>，平台单只查 return:<return_sn>。默认方案：平台事件建单前，先查同商户、同订单、同类型的未结手动工单；查到就把售后单挂到这张工单上，转为平台驱动，dedupe_key 改为 return:<return_sn>，并在时间线写「平台事件接管」。需要修改 DESIGN 11.4 的 create 守卫。

### DP-06 平台驱动的工单禁止手改时限

来源：tickets-05。TikTok 退货单在「等买家」阶段可以手改时限，改完被标成「商户时限 · 按接待设置」，下一条平台事件到来又会把它静默覆盖。这与 REQ-TKT-001 和 PAGE-RECEPTION-TICKETS「平台类时限只读」冲突。默认方案：platformDriven=true 的工单一律禁用改时限，API-TKT-008 返回 409。需要修改 API-TKT-008 的 409 条件。

### DP-07 明确 Shopee 售后各状态下可执行的动作，以及 ACCEPTED 是否算终态（P1）

来源：e2e-service-03、e2e-service-13。退货退款类在 REQUESTED 阶段就能一键「同意退款」，货还没寄回钱就退了，而且这个选项默认选中。ACCEPTED 在 11.13 被算作未终结，在 11.4 又映射为已解决，导致右栏一直留着「处理」按钮。默认方案：退货退款类在 REQUESTED 阶段只给「发起争议」和等待说明，PROCESSING 且已有寄回运单时才给「同意退款」，仅退款类保持现状；ACCEPTED 定为终态，open=false。TEST TC-ORD-013 要同步修改。修复组 O-04 先去掉默认选中做止血。

### DP-08 会话晚于平台工单建立时，回填工单的 conversation_id（P1）

来源：workbench-act-02。买家先申请售后、后发消息时，自动建的工单 conversation_id 为空：右栏写「这个会话没有未结工单」，列表行也没有徽标，转交时勾选「关联工单一并转交」带不上这张单，但订单卡的处理弹层里又写着这张工单的单号。默认方案：会话建立或重开时，按店铺、买家 ID 和订单号，把未结工单的 conversation_id 回填；备选是会话详情的 openTickets 改按「本店本买家的订单」取。需要修改 REQ-CONV-002、REQ-CONV-003 与 11.4。

### DP-09 待认领置顶的排序，以及「AI 草稿」分组的命名

### DP-10 发票聊天发送失败，在会话里重试成功后要回写发票状态

### DP-11 订单同步失败的状态与展示

### DP-12 用量提醒的渠道只保留一个设置入口

来源：admin-03（P2）。/billing 的提醒弹层与 /settings/notify 各设一套渠道，新商户两处的默认值就不一致。发送时邮件强制取 alertConfig.email，「通知」页的邮件开关不起作用；而它的站内开关又能悄悄压掉用量页打开的站内提醒。REQ-BILL-004 与 REQ-SET-002 在这件事上重叠。默认方案：渠道只在 /billing 设置，「通知」页这一行改为只读并链到用量页；两处默认值统一。

### DP-13 收窄成员负责店铺时，如何处置他在被移出店铺里的处理中会话与未结工单

来源：e2e-onboard-03（与 server S-09 同一根因）。取消某家店的负责后，他在该店处理中的会话仍挂在他名下，但他已经打不开，分配弹窗也没有任何提示。默认方案：按停用的规则释放——会话退回待认领并写时间线，工单退回该店组长；分配弹窗在保存前显示影响数量。需要补 REQ-TEAM-003 与 §16。

### DP-14 401 响应带原因码，登录页据此说明为什么被退出

来源：e2e-onboard-09。被停用、会话被吊销、会话过期这三种情况，都是跳到一个普通登录页。默认方案：401 带 code（member_disabled、session_revoked、session_expired），跳转时附上 reason，登录页显示一行对应说明。这会改 DESIGN §14 的 /errors/unauthenticated 和 contracts。shell-shared H-16 先做一条通用提示。

### DP-15 决定「确认邮箱」要不要真正验证

来源：auth-shell-14。验证邮件里的链接只是 /login?verified=1，不带令牌，也不做任何确认。默认方案：本期不做邮箱验证，改邮件文案、去掉「确认邮箱」按钮。如果要做，就用一次性令牌写 user.emailVerified 并显示结果，同时补 REQ-AUTH-001 的验证状态定义。

### DP-16 已有账号的人能否再新建一个商户

来源：auth-shell-31。REQ-AUTH-004 允许一个账号属于多个商户，原型的账号弹层里也有「新建商户」，但 REQ-AUTH-001 只支持用新邮箱注册。默认方案：本期明确不支持，把原型里的这个入口记为不实现；要支持的话，再加「已登录用户只填商户名和时区」的流程。

### DP-17 定义 TikTok 订单「买家名」取哪个字段

来源：orders-07（P2）、workbench-act-22。现在 TikTok 订单的 buyerName 取的是打码后的收件人名，列表、抽屉、售后弹层与会话里的名字对不上，按买家名也搜不到。DESIGN §9.4 没有定义来源，改它会改变接口输出的含义。默认方案：读取订单时按 (shop, buyer_external_id) 取会话里的买家昵称（TikTok 会话的 buyer_external_id 存的是 user_id，与订单的 user_id 一致），找不到时回落到收件人名；收件人名只出现在收件信息里；订单搜索同时匹配这个昵称。

### DP-18 draft_generated 要不要写进审计日志

来源：admin-28。每份 AI 草稿都写一条审计，近 30 天有 48 条，人工的配置变更被淹没；审计行也不能点开查看对象。默认方案：draft_generated 不写审计（只计数），或者归入默认隐藏的「系统」来源；审计行为 targetType/targetId 生成链接。

### DP-19 提醒类通知的规则：写进工单时间线、无组长时的兜底、按店合并

来源：e2e-ops-23、e2e-ops-24。工单即将到期、已超时的提醒在工单时间线里查不到，通知也不写店铺和剩余时长。没有组长的店，待认领提醒逐条只发给所有者，一度堆到 41 条，另一位管理员一条也没收到。默认方案：ticket.scan 发提醒时同时写 ticket_event；待认领提醒在无组长时发给全部管理员，同一时刻同一店的多条合并成「店名 有 N 个会话待认领超过 10 分钟」。需要修改 11.1 与 REQ-CONV-010。

### DP-20 全局搜索支持发票号，消息结果能定位到具体消息

来源：e2e-ops-21、e2e-ops-22。买家来问时最常报的是发票号，但现在搜不到；点消息结果只打开会话，不滚动、不高亮命中的那条。默认方案：API-SEARCH-001 增加 invoices 分组（按编号前缀匹配，范围同订单）；消息结果链接带 message 参数，API-CONV-002 支持 around=<messageId>。这两项都会改 contracts。

### DP-21 别人处理了指派给你的工单时，通知负责人

来源：e2e-service-15。组长在工单页替员工完成了退款，员工本人没有收到任何通知，可能会重复联系买家。默认方案：在 REQ-SET-002 的事件清单里加一类「工单被他人推进或解决」，只通知负责人。

### DP-22 会话右栏能查看这个买家已结束的工单

来源：e2e-service-25。工单解决后，右栏只写「这个会话没有未结工单」，「全部工单」链接跳到不带筛选的 /tickets，从会话里追溯不到历史工单。默认方案：在工单小节下折叠显示「已结束的工单 N 张」，「全部工单」带上买家筛选。需要同步修改 ui-interactions 里写的跳转目标。

### DP-23 链接与发信类接口返回更细的原因

来源：admin-16、auth-shell-32（旧链接文案部分）、auth-shell-13（预检部分）、admin-15。三种情况都需要改 contracts：
- 重发邀请后打开旧链接，提示「不完整或不存在」，应提示「已被新邀请替换」，需要新增 code: replaced；

### DP-24 /tickets 新建工单可以关联订单，平台类类型必须关联订单

### DP-25 按实现修订 DESIGN §9.4 的订单状态筛选标签

来源：orders-24。DESIGN 写的 8 个标签与 statusGroup 枚举对不上：缺 unpaid 和 in_cancel，多出「待揽收」。实现用的 8 项与枚举一一对应，更合理。只改 DESIGN 与 ui-interactions，代码不用动。

### DP-26 contracts 里的校验文案改成面向用户的中文

来源：auth-shell-16（商户名超长部分）、e2e-onboard-20（空邮箱部分）。商户名超长时显示「数值过大：期望 string <=80 字符」，空邮箱时报「邮箱格式不对」。文案定义在 src/contracts/auth.ts 的 zod message 里，不属于任何修复组。默认方案：max 写「商户名最多 80 个字」，必填与格式拆成两条消息；类型和字段都不变。
